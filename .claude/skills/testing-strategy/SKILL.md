# Testing strategy: lessons

## Tiers and speed

- Put each test in the cheapest tier that can catch its bug: logic in unit tests, external systems in contract tests against recorded responses, end-to-end only for a few smoke paths in the batch tier. Why: a full verify of 18–20 min, run 3–5× per ticket, was the main cost of every ticket. Source: pesitro retro 2026-10-21.
- Build contract fixtures from recorded real responses, never from the API docs alone. Why: swagger-derived fixtures passed while the live ERP prefixed columns, returned zero prices and rejected a field; every mismatch surfaced only after merge. Source: pesitro#179, #231–#234.
- Run the batch tier on a fresh database. Why: e2e state leaked between tests on the dev database, so local green met CI red. Source: pesitro#216.
- When verify fails only on timeouts in tests outside the ticket (a different set each run), re-run just the failed specs once; when they pass, report it and let CI decide. Why: two hours went into five full verify runs chasing load timeouts after a 15-minute fix. Source: pesitro#183.
- Prove a flaky fix with `--repeat-each=5` (or the runner's equivalent) before calling it fixed. Source: pesitro#141.

## Red: the test must fail for the right reason

- A red test fails on its assertion about the missing behaviour. Failing on an unrelated error (HTTP 500, fatal, timeout) proves nothing; stop and find out why. In an interpreted language planned-but-missing interface counts as missing behaviour: class not found, undefined method, wrong argument count. Source: pesitro#55, #150, #154, #157.
- In a compiled language the red commit compiles: it carries the new tests plus stubs whose body is only a throw, and nothing else. Check: the red run shows assertion failures or the stub's exception, never a compile error, and `git show --stat <red-sha>` lists only tests and stubs. Why: a red that did not compile broke bisect and per-commit CI, one carried the whole refactor, and one "stub" was the finished body behind `if (true) throw`, so its green was a six-line deletion. Source: elsteo#223, #224, #225, #255, #269.
- A test that is green the moment it is written gets a mutation check: break the line it guards, watch it fail, restore it by reversing that one edit (never `git checkout -- .` or `git restore .`, which also drop your uncommitted work; or commit first) and `git diff` the file to see only your intended change remains, since a text replace can hit an earlier identical occurrence, and report the mutation. Data-provider rows expecting `false` need this most, because a renamed key keeps them green for the wrong reason. Source: pesitro#152, #179; restore: Servisnik#118, #121, #135.
- A `test:` commit rebuilt after the fact (to split a branch or fix commit order) is run on its own exported tree before the `feat:` that follows, and the red result is noted. Why: rebuilt commits were made from final file contents, so nobody had seen them fail; a reviewer had to replay four commits to prove it. Source: Servisnik#102.
- A guard against a race (a row changed or deleted while this transaction waited for its lock) gets a test that drives that race with two connections, not only the happy path. Why: two "deleted while waiting" branches could be removed with every test green. Source: Servisnik#96.
- A test that forces a PostgreSQL deadlock gives the side that must lose a short `deadlock_timeout` and the other a long one, and asserts what the loser does next (the retry count). Why: PostgreSQL checks for a deadlock once per lock wait, so under load the wrong side became the victim after 30 s, the test timeout, and a test written against flakes flaked. Source: Servisnik#134.
- Every rule and invariant in the plan has a test that fails when the rule is mutated. Before reporting done, walk the plan's rules one by one and name each one's test. A query filter (`where user = …`, `where role = admin`) is a rule too: its test holds a row the filter must leave out and asserts that row is untouched or uncounted. Why: a seed's session delete without its user filter and its admin count without its role filter both stayed green, because each test held a single user. Source: pesitro#150, #155, Servisnik#143.
- A deviation from the plan, even a more cautious one, gets its own test. Source: pesitro#155.

## Green: implement only what the current test demands

- The first `feat:` commit carries only the behaviour the current red test asks for. Extra values, branches and guards arrive with the tests that demand them, and a helper ported from deleted code arrives with the test that ports it. Why: pre-built branches made later tests green on arrival, five times over. Source: pesitro#35, #157, #158, #205, #218.
- Keep `test:` commits pure, and amend a test only while it is still red. A test changed during implementation (a weakened assert, a fixed setup) goes in a new `test:` commit before the `feat:`. Why: an amend hid that `assertCount(1)` had been weakened to `assertNotEmpty`. Source: pesitro#131, #154.

## Shapes that slip through

- An ordering rule ("check A, then B") gets a test whose input satisfies both conditions at once. Source: pesitro#159.
- When a plan lists what a branch must *not* do (no write, no note, no email, no log), assert every item, and include a row for the last retry attempt. Source: pesitro#204.
- Code that reads "all records" gets a test with more records than the framework's default page size. Source: pesitro#157.
- A "no configuration changes nothing" test compares the whole captured state with strict equality, never a subset match. Source: pesitro#189.
- A test that bypasses the real path (order via API instead of checkout) claims only what it covers; the real path's totals are asserted in its own test. Why: the API path rounded VAT to 0.66, checkout to 0.65. Source: pesitro#149.
- A stub that stands in for a framework call (a hook, a client) returns what the code under test hands it, such as the initial state, unless the test sets an answer. Check: change the value the code passes and watch the test fail. Why: a `useActionState` stub ignored the form's initial `null`, so changing it to an error showed an alert on every page load with all tiers green. Source: Servisnik#146.
- A rule that lives in a template or view is tested by rendering it over temporary data, not by calling the helper it uses. Source: pesitro#228.
- A refactor or a dedup ("covered by the other file") that deletes tests maps every deleted assertion to a surviving or new one, and proves each mapping by deleting the guarded line and watching a test fail; a fixture's teardown assertion counts too and keeps a failing case that runs through the fixture itself. Why: extracting an e2e fixture's checks into a helper left the fixture's own `expect` with no failing case, so deleting it kept every tier green; a test a design dismissed as "string plumbing" was the only test of an env parser. Dropping duplicate print tests as covered elsewhere lost the only missing-glyph check on a page with €. Source: pesitro#157, Servisnik#86, #139, elsteo#225, #226, #227, #228.
- A test that claims "unchanged" compares against a baseline: a committed fixture of the old output, or the old implementation run beside the new one. Check: for each such test, name where the expected values come from and re-derive each assertion from the new code; any that cannot fail goes. Why: a catalog "unchanged" test compared a function with a list built from that same function, and asserted none of the labels the design said were preserved. Source: elsteo#254, #255.
- A test generated over a registry pins how many cases it produced, and exempts cases only by a literal list of names. Check: forcing the exemption condition true for one extra case turns the suite red. Why: a 112-case matrix routed any case that threw into a weaker arm that skipped the ticket's own proof, and nothing asserted the matrix still had 112 cases. Source: elsteo#252, #255.
- A rule "X does not stop the loop" is tested with X before the last element and asserts that a later element still succeeded; "X stops the loop" needs an element after X. Why: every row-fault test put the faulting row last, so the continue half never ran and the docs had it backwards. Source: elsteo#250.
- A test only the gate can run (needs an SDK, certificate or live sandbox) copies its request and assertions from a twin the normal suite runs, and closes what it opened when it throws. Why: a gate-only test failed on its own assertion after the external system had accepted the filing, so the run lost its only record of it. Source: elsteo#256.
- A test that reports state involving a secret prints only whether it matched (`password: matches`), never the value. Source: pesitro#189.
- A data migration that re-implements a domain function in SQL (a backfill of normalized keys) gets a test that inserts rows before running the migration and expects the domain function's output, including the awkward inputs (decomposed Unicode, foreign diacritics, non-breaking spaces). Why: the migrated test database is empty, so a backfill that covered only 44 Slovak letters stayed green while the domain stripped every diacritic. Source: Servisnik#70.

## Checks are code too

- Every custom check (lint script, budget, boundary rule) has its own test with one example that passes and one that fails, asserting the exact violation list. A pattern check's passing example also holds a near-miss for every guard (look-around, word boundary, character class), so deleting the guard turns it red. Its CLI wrapper is only the line that reads argv; everything else is exported and tested. Why: a silently broken check is a false green, and an autonomous run trusts green. Source: pesitro#97, #224; near-miss: Servisnik#92, where five guards could be deleted with every test green.
- A completeness test ("every exported X has a row") that skips files or filters exports by type pins the exact export list of each skipped file and fails on any export that is neither in the table nor pinned. Why: an access table test skipped its helper files and counted only `typeof === 'function'`, so the next unguarded function in the most likely file would never have been tested. Source: Servisnik#118.
- A check over git history keeps per-commit state inherited from each commit's first parent, never one flag over a `--topo-order` list, and reads changed files with `--no-renames`. Why: a ticket branch that merged its base mid-branch passed its own PR but would fail the integration PR, and a `feat` that renamed a test file away listed only the new path and passed. Source: Servisnik#87.
